# 공식 문서 문안 규약

## 먼저 읽을 것

**이 문서만 읽고 글을 쓰기 시작하지 않는다.** 이 문서는 공식 문서 전용 조항만 갖는다. 한국어 산문의
일반 규칙은 같은 스킬의 다른 두 파일에 있고, 건너뛰면 규칙의 절반이 빠진 채로 쓰게 된다.

| 읽을 것 | 무엇 |
|---|---|
| `../../../output-styles/fluent-korean.md` | 지침 원문. 문장과 구를 어떻게 맺는가 |
| `expressions.md` | 이 저장소에서 실제로 지적받은 말 |

원문은 **사본이며 고치지 않는다.** 갱신은 원저장소에서 다시 받아 통째로 갈아 끼우는 방식으로
한다. 경로와 커밋은 스킬의 `SKILL.md` 에 적혀 있다. 우리 조항은 전부 `expressions.md` 로 간다.

### 원문의 조항은 실제로 자주 어긋난다

엠대시와 비유적 어휘가 특히 자주 들어간다. 둘 다 원문의 「구 단위」가 이미 다루는 조항이므로, 이
문서의 조항을 지키기 전에 원문을 먼저 읽는다. 좁은 칸에 많은 내용을 담으려는 압력이 조각마다 붙는
설명 칸에서 특히 강하게 작용한다.

## 소관 경계

조항이 갈라져 있으므로 어느 문서를 펼칠지 먼저 정한다. 아래는 색인이지 요약이 아니다.
**다른 두 파일의 소관 항목을 이 문서에 옮겨 적지 않는다.** 원문이 요약을 금지하는 이유를 스스로
밝히고 있고(「상황과 목표」), 두 벌이 되면 한쪽만 갱신되는 순간 어긋난다.

| 축 | 소관 |
|---|---|
| 엠대시, 종결어미로 문장 맺기, 조사·어미 생략, 비유적 어휘, 한자어 활용, 문장 성분 생략 | `../../../output-styles/fluent-korean.md` |
| 이 저장소에서 지적받은 말(동사 어간으로 만든 명사, `가른다`, 공학 용어 비유) | `expressions.md` |
| 공문서투, 번역투 다섯 갈래, 늘어진 구조, 셋 이상의 나열, 두괄식, 제목 | 이 문서 |
| 작업 이력·협업 절차를 남기지 않기, 부정으로 정의하지 않기, 완결형으로 적기 | 이 문서 |
| 문체 두 갈래, 그림과 글의 어긋남 | 이 문서 |

## 적용 대상

공식 문서의 한국어 글은 두 갈래다. 도구가 무엇이든 이 구분은 같다.

| 갈래 | 무엇인가 | 문체 |
|---|---|---|
| 규격 | 조각 하나하나가 무엇이고 어떤 값을 갖는지 적은 설명 | 다체 |
| 안내 | 파일이나 페이지를 처음 여는 사람에게 건네는 설명 | 합쇼체 |

**적용한다**

- 조각 하나하나의 규격을 적은 설명
- 페이지나 파일을 처음 여는 사람에게 건네는 안내문
- 페이지 머리의 한 줄 역할과 소개
- 명세표의 비고 칸

**적용하지 않는다**

- 도구가 식별에 쓰는 이름(노드 이름·변수 이름·도구가 코드와 잇는 데 쓰는 값)
- 그림의 아트보드 이름과 짝인 표기(화면 제목의 `/tasks — default` 형식, 라우트 주소). 여기의
  엠대시와 기호는 조항의 대상이 아니므로 글자 하나도 고치지 않는다
- 코드의 축 이름을 그대로 옮긴 격자 머리행·행 이름
- 명세표의 토큰·CSS·값 칸
- 예시 안의 더미 글자와 버튼 라벨
- 스크립트의 주석과 반환 문자열
- 저장소 문서

더미 글자는 제품 화면의 글이라 이 규약이 아니라 제품 UI 문안 규칙을 따른다. 문체를 맞추려 들지
않는다. 버튼 라벨은 「확인」이다. (이 저장소에서는 `docs/design-system/FIGMA_PAGE_SPEC.md` §9 가
그 규칙을 갖는다.)

저장소 문서는 원문과 그 저장소의 관례를 따른다. 이 저장소의 경우 `CLAUDE.md` 가 `docs/**` 와
규약 문서에 `fluent-korean` 지침을 걸어 두었고, 이 문서의 원칙과 문안 조항은 거기에 강제되지
않는다.

도구마다 그 두 갈래가 어느 자리에 담기는지는 「도구별 주의」에 적는다.

## 문체

| 갈래 | 문체 | 예 |
|---|---|---|
| 규격 | 다체 | 아코디언의 한 줄이며, 트리거와 본문을 묶은 단위다. |
| 안내 | 합쇼체 | 이 파일의 변수와 컴포넌트는 코드의 토큰·클래스와 이름으로 대응합니다. |

규격은 값을 확인하러 오는 자리라 저장소의 규약 문서와 같은 다체를 쓴다. 안내문은 문서를 처음
여는 사람에게 건네는 설명이라 저장소의 설명 문서와 같은 합쇼체를 쓴다. (이 저장소의 경우 전자는
`CLAUDE.md` · `.claude/*.md` · `docs/design-system/FIGMA_*_SPEC.md` 이고 후자는
`docs/design-system/README.md` 다.)

두 문체를 하나로 통일하지 않는다. 규격은 단정하는 글이고 안내는 건네는 글이라 어미가 다르며,
한쪽으로 몰면 그쪽이 자기 갈래에 맞지 않는 어미를 쓰게 된다.

⚠ 문체는 도구나 폴더가 아니라 글의 갈래가 정한다. 한 파일 안에서도 규격은 다체이고 안내는
합쇼체다.

## 원칙

### 1. 지금의 규격만 적는다

문서는 시스템이 지금 어떤 모습인지를 적는다. 거기에 이르기까지의 경로는 적지 않는다.
실제로 걷어낸 문구다.

- 「이번에 새로 뚫은 층입니다」
- 「종전에는 제목이 일곱이었고 그중 넷을 없앴습니다」
- 「원래 쓰던 문구는 버리지 않고 설명 줄로 옮겨 적습니다」
- 「(2026-09-06 신설)」

「이번에」·「종전에는」·「신설」과 괄호 안 날짜는 전부 같은 갈래다. 문서를 여는 사람은 지금
규격을 보러 온 것이지 그 규격이 어떻게 정해졌는지를 보러 온 것이 아니다.

변경 경위는 자리가 따로 있다. git 이력과 저장소 문서가 그 자리이고, 거기에서는 날짜와 실측을
그대로 적는다. **이 조항은 공식 문서 안의 글에만 적용된다.**

사유를 적어야 하는 ⚠ 문단에서도 「누가 언제 무엇을 고쳤다」가 아니라 「왜 이 값이어야 하는가」를
적는다.

```
전  2026-09-06 에 파일 트리만 접힘을 Chevron Right 로 쓰고 있어 Accordion 쪽으로 맞췄다.
후  파일 트리는 아래로 펼쳐지므로 접힘은 ∨, 펼침은 ∧ 를 쓴다.
```

### 2. 협업 절차를 적지 않는다

걷어낸 문구다.

- 「결과를 코드에 옮기는 일은 에이전트가 MCP 로 이 파일을 읽어 수행합니다」
- 「코멘트로 알려 주십시오」
- 「코멘트로 남겨 주십시오」

누가 어떤 도구로 작업하는지, 무엇을 어디에 알리는지는 팀의 운영 방식이지 컴포넌트의 규격이
아니다. 운영 방식은 바뀌는데 공식 문서는 그 변화를 따라가지 못해 곧 틀린 안내가 된다.
운영 규약은 저장소 문서가 갖는다.

### 3. 무엇인지 먼저 적는다

「A 가 아니라 B 다」로 정의를 시작하지 않는다. 읽는 사람이 A 를 한 번 떠올린 뒤 지워야 하고,
지운 자리에 B 하나만 남는다면 A 는 처음부터 없어도 되는 문장이다.

다만 대비 자체를 금지하는 것은 아니다. 둘을 이렇게 나눈다.

| 갈래 | 꼴 | 판정 |
|---|---|---|
| 부정으로 시작하는 정의 | 「이 파일은 화면을 그린 그림이 아닙니다」 | 쓰지 않는다 |
| 의미를 좁히는 대비 | 「`hover` 는 prop 이 아니라 CSS 상태다」 · 「Badge 는 누를 수 없다. 누르는 것은 Button 이다」 | 그대로 쓴다 |

나누는 기준은 지목한 쪽을 실제로 헷갈릴 사람이 있는가다. `hover` 를 prop 으로 여겨 변형 축에
세우는 일은 실제로 일어나므로 그 대비는 규격의 일부다. 파일을 그림으로 여기는 사람은 없으므로
그 부정은 강조에 그친다.

### 4. 완결형으로 적는다

읽는 사람에게 말을 거는 꼴, 부탁하는 꼴, 물음을 던지는 꼴을 쓰지 않는다.

| 갈래 | 전 | 후 |
|---|---|---|
| 상황을 묻는 라벨 | 버튼이 너무 큽니다 / 작습니다 | 컨트롤 크기 |
| 서술형 제목 | 세 층으로 나뉩니다 | 세 층 구조 |
| 부탁형 어미 | 쓰지 마십시오 | 쓰지 않습니다 |
| 제목의 개수 | 규칙 넷 · 지켜 주셔야 하는 것 넷 | 규칙 |
| 명사만 나열한 제목 | 변경 지점 | 값을 바꾸는 곳 |

- 공식 문서 안의 제목과 라벨은 명사구로 맺는다. 원문 「문장 단위」 2번이 헤더와 목록을
  강제 대상에서 뺀 자리가 여기다. 저장소의 규약 문서는 이 조항이 아니라 그 저장소의 관례를
  따른다.
- ⚠ **예외가 둘 있다. 문서 세트의 골격 제목과 데이터베이스 행의 절 제목은 물음꼴로 둔다.**
  골격 제목은 그 자리에 무엇을 적어야 하는지를 지시하는 장치다. 「무엇을 놓아주는가」를
  「놓아준 것」으로 바꾸면 빈 문서를 받은 사람이 무엇을 채울지 알 수 없게 된다. 골격을 정한 규약이
  정본이므로 그 제목을 개별 문서에서 고치지 않는다. **예외는 이 둘뿐이고 나머지 제목은 명사구다.**
- **제목에 개수를 붙이지 않는다.** 항목에 번호를 매기는 것과는 다른 문제다. 「함정 11~21」처럼
  찾아가기 위해 번호를 다는 것은 그대로 두고, 제목이 개수를 세는 것만 금한다.
- **명사만 나열한 제목은 쓰지 않는다.** 「변경 지점」은 무엇을 변경하는지가 빠져 있어 뜻이
  좁혀지지 않는다.
- 본문은 종결어미로 맺는다. 안내문은 「~하지 않습니다」, 규격은 「~하지 않는다」다.
- 금지를 강하게 못 박는 ⚠ 문단에 한해 규격에서 「~하지 말 것」을 쓴다.
  「~해 주십시오」는 어느 자리에도 쓰지 않는다.

## 문안 조항

공공언어 기준과 테크니컬 라이팅 실무 지침에서 가져온 것이다. 출처는 맨 끝 「근거와 출처」에 있다.

| 갈래 | 규칙 | 예 |
|---|---|---|
| 공문서투 | 「및」을 쓰지 않는다 | 토큰 및 클래스 → 토큰·클래스 |
| 번역투 | 「~적」을 뺀다 | |
| 번역투 | 불필요한 「~의」를 뺀다 | |
| 번역투 | 「여러/많은 + ~들」의 복수 접미사를 뺀다 | |
| 번역투 | 「~에 의하여」를 「~이/가」로 바꾼다 | |
| 번역투 | 「~로부터」를 「~에게/~에서」로 바꾼다 | |
| 문체 | 사람이나 서비스가 주체이면 능동형을 쓰고, 이중 피동을 쓰지 않는다 | 잡혀지다 → 잡히다 |
| 어휘 | 어려운 한자어 대신 쉬운 말을 쓴다 | 착수하다 → 시작하다 |
| 어순 | 수식어를 피수식어 바로 앞에 두고 주술 호응을 맞춘다 | |
| 외래어 | 국립국어원 표기를 따른다 | 리포지터리 · 애플리케이션 · 라이선스 · 업그레이드 |
| 전문용어 | 꼭 필요할 때만 쓰고, 쓰면 그 자리에서 설명한다. 문서 전체에서 같은 용어를 쓴다 | |

### 늘어진 구조를 서술어로 편다

「~하는 것은 ~위해서입니다」·「~하는 것은 ~때문입니다」는 주어를 명사절로 부풀린 뒤 서술어를
뒤로 미룬 꼴이다. 서술어를 앞으로 당겨 한 문장으로 편다.

```
전  차례를 고정하는 것은 62장 어디에서나 같은 종류를 찾기 위해서입니다.
후  62장 어디에서나 같은 자리에서 같은 종류를 찾도록 차례를 고정합니다.
```

### 셋 이상을 나열할 때는 가운뎃점을 쓴다

```
전  hover 와 focus 와 disabled 와 aria-invalid 는
후  hover · focus · disabled · aria-invalid 는
```

⚠ 원문 「구 단위」 1번의 조사 생략 금지와 어긋나 보이지만 어긋나지 않는다. 그 조항은 문장
성분 사이의 관계를 드러내라는 것이지, 나열 항목마다 접속 조사를 붙이라는 것이 아니다. 마지막
항목에 붙는 조사 하나가 관계를 이미 드러낸다.

### 두괄식으로 규칙을 먼저 적는다

규칙을 앞에 두고 사유를 뒤에 붙인다. 사유를 먼저 늘어놓으면 읽는 사람이 결론을 기다리며 읽어야
한다.

```
전  쪼갠 것을 보여 주었으면 조립한 것도 함께 보여 줍니다. … 그래서 컴포넌트 페이지마다
    「예시」를 둡니다.
후  컴포넌트 페이지마다 「예시」를 둡니다. 원본은 계약이므로 …
```

## 그림을 고치면 그 그림을 설명하던 글도 함께 본다

그림과 글이 한자리에 담기는 문서에서는 둘이 따로 어긋난다. 디자인 시스템 파일에서
Dropdown Menu 의 라디오 표시자를 점에서 체크로 바꾸었을 때 「점은 오른쪽 끝에」라고 적힌 설명이
두 곳 남아 있었다.

같은 사실을 두 자리에 적었다면 고칠 때도 두 자리를 본다. 이 어긋남은 그림을 품는 도구라면
어디서나 생기므로 도구별 조항이 아니다.

## 교정 예시

```
전  이 파일은 그림이 아니라 제품의 정본입니다. 여기 변수를 바꾸면 코드가 따라 바뀌고,
    코드를 바꾸면 여기가 어긋납니다. 그래서 디자인 논의는 이 파일에서 하고,
    결과를 코드에 옮기는 일은 에이전트가 MCP 로 이 파일을 읽어 수행합니다.
후  이 파일의 변수와 컴포넌트는 코드의 토큰·클래스와 이름으로 대응합니다.
    한쪽만 변경하면 그 대응이 끊어집니다.
```

부정으로 시작하는 정의(원칙 3), 협업 절차(원칙 2), 공문서투 「및」을 함께 걷어낸 자리다.

```
전  아코디언 한 줄 — 트리거와 본문을 묶은 단위.
후  아코디언의 한 줄이며, 트리거와 본문을 묶은 단위다.

전  Dialog 와 같은 면이다 — popover 바탕 · surface/radius 12 · 안쪽 링 ring-subtle 1.
후  Dialog 와 같은 면이다. popover 바탕, surface/radius 12, 안쪽 링 ring-subtle 1 을 쓴다.
```

엠대시로 이어 붙인 뒤 명사구로 끝낸 꼴이다. 요약 한 줄에서 가장 자주 나온다.

```
전  리터럴로 남긴 값(CSS 헤더가 못 박음 — 크기 축 3단 × 방향 2 가 곱해지는 자리라
    축이 아니라 표다)
후  리터럴로 남긴 값(CSS 헤더에 사유가 적혀 있다. 크기 축 3단과 방향 2 가 곱해지는 자리라
    축이 아니라 표에 가깝다)

전  destructive 는 color-mix(...) — 바인딩 뒤 opacity 0.9 를 얹었다(경고문 전체가 붉으면
    제목이 묻힌다).
후  destructive 는 color-mix(...) 다. 변수를 묶은 뒤 opacity 0.9 를 함께 주었는데,
    경고문 전체가 붉으면 제목이 눈에 들어오지 않기 때문이다.
```

비유적 어휘(못 박다·얹다·묻히다)를 일반 어휘로 되돌리고, 괄호 안에 눌러 담은 사유를 문장으로
편 자리다.

## 내보내기 전 점검

### 원문 소관

1. `../../../output-styles/fluent-korean.md` 의 「문장 단위」·「구 단위」 조항을 훑는다. 실측에서는
   엠대시(구 단위 4번)와 비유적 어휘(구 단위 3번)가 특히 자주 어긋났다. 조항의 내용은 그
   문서에서 읽는다.

### 문안 소관

2. 「및」이 남아 있는지 본다. 가운뎃점이나 「와/과」로 바꾼다.
3. 번역투 다섯 갈래를 본다. 「~적」, 불필요한 「~의」, 「여러/많은 + ~들」, 「~에 의하여」,
   「~로부터」다.
4. 「~하는 것은 ~위해서입니다」·「~때문입니다」로 늘어진 문장이 있는지 본다.
5. 셋 이상을 「와/과」로 이어 붙인 나열이 있는지 본다.
6. 제목이 개수를 세고 있는지, 명사만 나열해 뜻이 좁혀지지 않는지 본다.
7. 이중 피동과 어려운 한자어가 남아 있는지 본다.
8. 외래어 표기가 국립국어원 기준인지 본다.
9. 사유가 규칙보다 앞에 나오는 문단이 있는지 본다.

### 원칙 소관

10. 「이번에」·「종전에는」·「신설」과 괄호 안 날짜가 남아 있는지 본다.
11. 「코멘트」·「에이전트」·「MCP」·「~해 주십시오」가 남아 있는지 본다.
12. 부정으로 시작하는 정의가 있으면, 지목한 쪽을 실제로 헷갈릴 사람이 있는지 따진다.

### 문서 전체 소관

13. 자리에 맞는 문체인지 본다. 규격은 다체, 안내문은 합쇼체다.
14. 그림을 고쳤다면 그 그림을 설명하던 글도 보았는지 확인한다.

### 도구별 소관

15. 그 도구의 절이 있으면 거기에 적힌 확인 항목을 본다. 지금은 절이 없다.

## 도구별 주의

여기까지가 도구를 가리지 않는 조항이다. 아래는 도구 하나가 문안을 어떻게 저장하고 어떤 자리에
담는지에서 나온 조항이라, 그 도구를 쓸 때만 본다.

**지금은 절이 있는 도구가 없다.** 노션 페이지와 Claude Design 캔버스의 안내문이 이 규약의 대상이지만,
아직 이 규약으로 쓰면서 겪은 것을 실측해 두지 않았다. 겪은 것이 생기면 아래 형식으로 절을 추가한다.

### 도구가 늘면 여기에 절을 더한다

새 도구로 공식 문서를 처음 쓸 때는 아래 넷을 확인하고, 확인한 것만 절로 적는다. **겪지 않은
것을 미리 적지 않는다.** 그러면 그 서술 자체가 이 규약이 금하는 사실 아닌 규칙이 된다.

| 확인할 것 | 무엇을 보는가 |
|---|---|
| 저장 형식 | 문안이 평문으로 저장되는가 서식이 붙는가. 서식이 붙으면 어떤 문법이고 어디까지 쓸 수 있는가 |
| 이스케이프 | 따옴표·홑화살괄호·`&` 를 넣고 다시 읽어 대조한다. 넣은 쪽에 흔적을 남기지 않고 화면에서만 드러나는 이중 이스케이프가 있다 |
| 정렬 | 공백으로 맞춘 칸이 화면에서 서는가. 등폭 글꼴인 자리에서만 선다 |
| 분량 | 한 칸에 들어가는 길이가 얼마이고, 넘치면 잘리는가 접히는가 |

절의 형식은 이렇다. 도구 이름을 제목으로 쓰고, 규격과 안내가 그 도구의 어느 자리에 담기는지와 어느
자리가 적용 대상이 아닌지를 표로 먼저 적은 뒤, 그 도구에서 실제로 겪은 것을 항목마다 하나씩 잇는다.
