# 테스트 이름으로 명세한다

이 저장소에는 요구사항에서 화면까지 내려가는 기획 문서가 없다. **명세가 사는 자리는 테스트
이름이다.** 테스트 이름은 틀리면 그 자리에서 빨개지므로 어긋난 채로 남지 못하고, 기획 문서는
틀려도 아무도 아프지 않아 조용히 썩는다.

`packages/notes` 와 `packages/access` 의 테스트 이름이 그 본보기다.

```
it("다른 테넌트의 쪽지는 공개여도 보이지 않는다. 공개는 그 테넌트 안의 공개다")
it("같은 테넌트의 다른 사람은 보여도 보관하지 못한다")
it("고객사의 사람은 agent 를 지나지 못한다. 고객에게는 아직 열지 않은 자리다")
```

무엇이 참인지가 앞에 있고, 왜 그런지가 대시 뒤에 있다. 이 두 조각이 종전 유저 스토리의 문장과
수용 기준이 하던 일을 그대로 한다.

## 어디에 쓰고 어디에 쓰지 않는가

되돌리기 비용으로 나눈다. 전부에 이 절차를 밟으면 예전 속도로 돌아간다.

| 되돌리기 비용 | 예 | 이 절차 |
|---|---|---|
| 싸다 | UI 배치, 문안, 내부 전용 화면 | 밟지 않는다. 바로 만든다 |
| 중간 | 화면 흐름, 목록의 정렬 | 이름만 먼저 짓는다 |
| 비싸다 | 앱의 문, 행 단위 술어(화면 · 도구 · MCP), 상태 전이, 스키마, 밖으로 나가는 알림 | 전부 밟는다 |

비싼 쪽은 대개 `packages/access` · 도메인 패키지(`packages/notes` · `packages/agents`)와 `supabase/migrations` 에
닿는다. 그 셋을 건드리면 비싼 쪽이라고 보아도 된다.

## 절차

### 1. 캐낸다

하고 싶은 것을 들은 다음, 답이 나오지 않은 질문을 묻는다. 종전에 유저 스토리와 수용 기준을
쓰면서 알아내던 것이 이 목록이다.

1. **누가** 그 자리에 서 있는가. 운영팀인가 고객인가, 그 테넌트에서 소유주인가 관리자인가 구성원인가.
   사람이 아니라 에이전트가 도구를 부르는 자리인가, MCP 로 붙은 사람의 토큰인가.
2. 그 사람이 그 순간 **무엇을 알고 싶은가.**
3. **무엇이 보이면 안 되는가.** 가장 자주 빠지고 가장 비싸게 틀린다. 다른 고객사의 행, 같은 조직의 비공개 행,
   남이 연 대화가 그 예다.
4. **경계가 어디인가.** 창의 길이, 기한, 개수, 포함하는 끝과 포함하지 않는 끝.
5. 같은 값을 보는 **다른 자리가 있는가.** 있으면 판정은 한 곳에만 둔다(REQ-02 의 자리). 앱의 문은
   `canEnterApp` 하나이고, 쪽지가 누구에게 보이는지는 `rules/visibility.ts` 의 `canSeeNote` 하나다.
6. 틀리면 **누가 아픈가.** 아픈 사람이 없으면 만들 것이 아니라 버릴 것이다.
7. 이미 있는 **불변식 가운데 걸리는 것이 있는가.** 그 도메인 패키지의 `src/invariants.ts` 를 읽는다.

3번과 4번의 답이 없으면 더 묻는다. 그 둘이 비어 있는 채로 만든 것은 대개 다시 만든다.

### 2. 이름을 짓는다

코드를 쓰기 전에 `it(...)` 목록을 먼저 적는다. 이 목록이 그 작업의 계약이다.

- **참이 되어야 하는 것을 한 문장으로 적는다.** 함수 이름을 되풀이하지 않는다. 무엇을 부르는지는
  파일이 이미 말한다.
- **왜 그런지를 대시 뒤에 붙인다.** 한 줄이면 된다. 이 조각이 나중에 이 판정을 무르려는 사람을
  멈춰 세운다.
- **경계는 양쪽을 각각 적는다.** 들어가는 끝과 들어가지 않는 끝이 다른 줄이다.
- **들어가지 않는 것을 적는다.** 보관한 쪽지, 다른 테넌트의 행, 문을 지나지 못하는 테넌트. 빠뜨리면
  아무도 그것을 시험하지 않는다.
- **문서를 번호만으로 가리키지 않는다.** 제목을 함께 적는다.

| 짓지 않는다 | 짓는다 |
|---|---|
| `dueSoon 이 동작한다` | `이레째까지 들어가고 여드레째는 들어가지 않는다` |
| `권한 없으면 에러` | `다른 고객사의 쪽지는 목록에 나오지 않는다. 거부와 부재를 구분하지 않는다` |
| `정렬 테스트` | `마감이 없는 일은 있는 것보다 뒤다. 기한이 정해진 일이 먼저다` |

확인받을 때는 이름 목록만 보이지 않고 다음을 한 묶음으로 보인다. 사람이 이름 뒤의 결정을 함께 보아야 확인이 뜻을 갖는다.

| 묶음 | 무엇 |
|---|---|
| 테스트 이름 | 층마다(순수 규칙 · 포트의 계약 · 유스케이스 · e2e) |
| 공개 인터페이스 | 이름이 붙을 함수 · 포트의 메서드 · 타입 |
| 불변식 | 새로 세우는 id 와 걷는 id |
| 스키마 | 새 표 · 제약 · 롤마다의 GRANT(새면 안 되는 롤에 주지 않는 것까지) |
| 가정 | 묻지 못해 지어 정한 것. 하나씩 확인받는다 |

### 3. 불변식을 인용한다

캐내는 동안 걸린 불변식이 있으면 이름에 정식 id 를 적는다.

```
it("INV-NOTE-01 비공개 쪽지는 쓴 사람에게만 보인다")
it("INV-AGENT-01 같은 운영팀의 다른 사람은 실행 번호를 알아도 열지 못한다")
```

- 표기는 `INV-<도메인>-<두 자리>` 다(`INV-NOTE-01` · `INV-ACCESS-04`). 도메인이 없는 저장소 규약은 `REQ-01` 이다.
- ⚠ **줄여 쓰지 않는다.** `INV-AGENT-04 · 06` 처럼 뒤쪽 접두사를 생략하면 긁는 쪽이 찾지 못한다.
- 종전에 도메인 함수를 가리키던 맨 번호(seam 번호)는 2026-09-14 에 폐기했다. 코드에 이름이
  있는 것에는 약어를 붙이지 않고 함수 이름을 그대로 쓴다. 판정 기준은
  `docs/decisions/2026-09-14-약어-규약.md` 에 있다.
- 카탈로그에 없는 규칙이 나왔으면 **그 도메인의** 카탈로그에 먼저 더한다. 없는 id 를
  인용하면 `npx turbo test --filter=@hathway/shared` 가 막는다.
- `status` 가 `enforced` 인데 인용하는 테스트가 없어도 막힌다. 새로 강제하기 시작했으면 올린다.

### 4. 빨간 것을 확인하고 만든다

절차의 나머지는 `tdd` 스킬이 갖는다. 이름을 적었으면 그쪽으로 넘어간다.

## 다 만든 뒤

- **기획 문서를 쓰지 않는다.** 무엇이 있는지는 라우트 디렉터리와 테스트 이름이 답한다.
- 고객이나 운영팀이 읽을 안내가 필요하면 `docs/` 에 쓴다. 그 문서는 틀리면 읽는 사람이 바로 묻으므로
  썩지 않는다.
- 왜 그렇게 정했는지가 남을 만하면 `docs/decisions/` 에 한 파일로 적는다. 한 번 적고 고치지 않는다.
- PR 본문은 문제와 영향과 근거를 담고, 리뷰를 받는 동안 **코멘트가 아니라 본문을 고쳐서** 최신으로
  둔다.
