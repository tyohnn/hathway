# 정보 구조를 짓는다

사랑받는 SaaS 의 공통점은 화면이 예쁜 것이 아니다. **다루는 핵심 객체가 분명하고, 날마다 되풀이하는 작업 루프가 짧다.**
IA 는 이 둘을 구조로 굳히는 일이다. 모양(색 · 간격 · 컴포넌트)은 tyohnn 이 맡고, 이 스킬은 그 앞에서 **무엇이 어느 화면에,
어느 그릇에 서는가**를 정한다.

차례는 **루프 → 객체 → 라우트 → 컨테이너**다. 거꾸로 하면(메뉴부터 그리면) 기능이 늘 때마다 사이드바가 무너진다.

## 먼저 제품의 꼴을 가른다

| 꼴 | 사용자가 하는 일 | 예 | 뼈대 |
|---|---|---|---|
| 관리형 | 내가 만든 것을 쌓고 고친다 | Flex · Linear · Notion 의 워크스페이스 | 객체 중심 사이드바 + 목록 → 상세 → 탭 |
| 생성형 | 입력하고 만들어 내고 다시 고친다 | ElevenLabs · v0 · Lovable | 도구 중심 사이드바 + 결과를 모으는 Library, 상세는 워크벤치 |
| 탐색형 | 남이 만든 것을 찾아 내 것으로 가져온다 | Notion 템플릿 · Figma Community · Viewtrap | 공개 스토어 셸 + 분류 체계 + 앱으로의 전환 |

한 제품에 둘 이상이 섞인다(Figma 는 관리형 + 워크벤치 + 탐색형). 섞이면 꼴마다 아래를 따로 하고 4번에서 셸로 나눈다.

이 파일은 세 꼴에 함께 드는 방법이다. 꼴마다의 해부도는 레퍼런스에 있고, 지도를 그리기 전에 해당하는 것을 읽는다.

| 꼴 | 함께 읽는 것 | 담은 것 |
|---|---|---|
| 관리형 · 생성형 · 워크벤치 | `references/dashboard.md` | 들어오는 모드 넷, 셸 · 홈 · 목록 · 상세 · 만들기 · 설정 · 역할 · 알림의 해부도, 생성형과 워크벤치의 차이, 지표 |
| 탐색형 | `references/store.md` | 들어오는 모드 셋, 분류 체계, 경로와 쿼리의 기준, 스토어에서 앱으로의 전환, 지표 |

## 1. 핵심 루프를 적는다

사용자가 하루에 여러 번 되풀이하는 루프 하나를 한 줄로 적고, **클릭 예산**을 정한다. 그 수가 IA 전체의 지표다.

| 제품 | 루프 | 예산 |
|---|---|---|
| ElevenLabs | 글 넣기 → 목소리 고르기 → 만들기 → 듣기 · 받기 | 홈에서 3 |
| v0 · Lovable | 프롬프트 → 만들기 → 미리보기 → 고치기 되풀이 | 홈에서 1 |
| Viewtrap · Viewstats | 검색 → 채널 · 영상 목록 → 상세 분석 → 저장 | 홈에서 2 |
| Flex | 구성원: 출퇴근 · 휴가 신청 / 관리자: 승인 · 조회 | 역할마다 1 |

- **루프는 홈에서 1 ~ 2 클릭이면 시작해야 한다.** 그 진입점이 홈의 맨 위에 선다.
- 역할마다 루프가 다르면 역할마다 적는다(Flex). 역할마다 홈이 다를 수 있다는 뜻이다.
- 루프는 많아야 둘이다. 셋째부터는 루프가 아니라 기능이다.

## 2. 객체를 모델링한다 (OOUX 의 ORCA)

기획 · 인터뷰 · brief 에서 명사를 뽑아 넷으로 정리한다.

| | 무엇 | 적는 것 |
|---|---|---|
| **O**bjects | 사용자가 부르는 이름이 있는 것 | 채널 · 영상 · 목소리 · 프로젝트 · 구성원 |
| **R**elationships | 객체 사이의 1:N · N:M | 워크스페이스 → 프로젝트 → 버전 |
| **C**TAs | 객체마다 할 수 있는 일 | 만들기 · 복제 · 공유 · 내보내기 · 보관 |
| **A**ttributes | 목록에 보일 것 / 상세에만 보일 것 | 이름 · 상태 · 고친 때 / 본문 · 기록 |

- **메뉴는 객체(명사)로 짓는다.** 기능(동사)으로 지으면 기능이 늘 때마다 메뉴가 는다. 객체로 지으면 새 기능은 그 객체 안의
  탭이나 CTA 로 들어간다.
- **예외: 생성형 도구.** 도구끼리 독립적이고 사용자가 「작업」으로 들어오면(ElevenLabs 의 TTS · 보이스 클로닝 · 효과음)
  도구별 메뉴가 맞다. 대신 결과물을 모으는 **History · Library** 를 하나 더 둔다. 결과물이 객체가 되는 자리다.
- 객체가 아닌 것을 객체로 세우지 않는다. 「통계」 · 「설정」 은 객체가 아니라 객체를 보는 관점이다(3번 「관점」).
- 객체마다 **누가 보는가**(테넌트 · 역할 · 쓴 사람)를 함께 적는다. 이 칸이 행 단위 판정이 되고, 비싼 쪽이다(`spec-by-test`).

## 3. 객체를 라우트와 그릇에 놓는다

| 이런 것은 | 이 그릇에 | 주소 |
|---|---|---|
| 혼자 존재하고 공유 · 북마크되는 객체 | **목록 라우트 + 상세 라우트** | `/projects` · `/projects/[id]` |
| 부모 없이는 뜻이 없는 종속 객체 | 부모 상세 안의 **탭** 또는 **시트** | `/projects/[id]/versions` |
| 같은 객체를 다른 관점으로 보기(통계 · 활동 · 설정) | 상세 안의 **탭** | `/projects/[id]/analytics` |
| 목록을 떠나지 않고 훑어보기 | **시트**(옆 패널) | `?selected=<id>` 또는 가로챈 라우트 |
| 칸 다섯 안팎의 짧은 만들기 · 고치기 | **다이얼로그** | 가로챈 라우트 `@modal/(.)new` |
| 긴 만들기 흐름(단계 · 미리보기) | **전용 페이지** 또는 단계 화면 | `/projects/new` |
| 지우기 같은 되돌릴 수 없는 일의 확인 | **알림 다이얼로그** | 주소 없음 |
| 속성 하나만 고치기 | **팝오버** · 제자리 편집 | 주소 없음 |
| 어디서든 쓰는 이동과 동작 | **⌘K 커맨드 팔레트** | 주소 없음 |

- **깊이는 목록 → 상세 → 탭까지다.** 그보다 깊은 화면이 필요하면 페이지를 더 만들지 않고 시트로 띄운다. 탭 안의 탭을 만들지 않는다.
- 목록은 기본으로 **표**(속성이 셋 이상이고 비교한다)인지 **카드**(그림이 주인공이다)인지 **목록**(제목과 한 줄이다)인지 고른다.
  같은 객체를 둘로 보여야 하면 한 라우트의 보기 전환(`?view=board`)이지 두 메뉴가 아니다.
- **같은 객체 · 같은 사람 · 같은 일이면 한 라우트다.** 일하는 사람이나 일이 다르면 따로 세운다. 접수 직원의 「오늘 예약」 표와
  원장의 「진료 일정」 달력은 같은 객체를 보지만 일이 달라서 두 라우트다. 몇 건뿐인 것(한 환자의 다가오는 예약)은 달력이 아니라 목록이다.
- 표가 아닌 큰 결정은 줄마다 **왜 그 그릇인가**를 한 줄 적는다. 그 줄이 나중에 「이거 페이지로 빼자」를 멈춰 세운다.

## 4. 라우트 그룹은 셸이 바뀌는 자리에서 나눈다

라우트 그룹은 메뉴의 분류가 아니라 **화면의 틀(셸)이 바뀌는 경계**다. 셸은 셋이다.

| 셸 | 생김 | 언제 | 예 |
|---|---|---|---|
| **공개** | 위 머리 · 아래 발치, 사이드바 없음 | 로그인 없이 보는 첫 화면 · 문서 · 스토어 | 랜딩 · Notion 템플릿 스토어 |
| **대시보드** | 사이드바 + 목록과 상세 | 관리형의 일상 | Flex · Viewtrap · ElevenLabs |
| **워크벤치** | 사이드바 없이 판 전체, 탭 대신 패널 | 한 객체 안에 오래 머물며 만드는 일 | Figma 파일 · v0 · Lovable 의 대화 + 미리보기 |

Figma · v0 · Lovable 이 몰입감 있게 느껴지는 것은 상세로 들어가는 순간 **셸이 통째로 바뀌기** 때문이다. 대시보드의 상세가
「오래 머물며 만드는 자리」라면 그 상세는 워크벤치 셸로 뺀다.

```
app/
├─ (site)/                     공개 셸: 랜딩 · 문서 · 새 소식 (· 스토어)
├─ login/ · no-access/         셸 없음
├─ (app)/                      대시보드 셸: 사이드바
│  ├─ page.tsx                 홈: 이어 하기 + 루프의 진입점
│  ├─ projects/
│  │  ├─ page.tsx              목록 ?q=&sort=&view=
│  │  ├─ @modal/default.tsx    가로채지 않을 때는 아무것도 그리지 않는다
│  │  ├─ @modal/(.)new/        목록에서 누르면 다이얼로그
│  │  ├─ new/                  주소로 바로 오면 전체 페이지
│  │  └─ [id]/
│  │     ├─ layout.tsx         상세 머리 + 탭
│  │     ├─ page.tsx           개요 탭
│  │     ├─ activity/          탭
│  │     └─ settings/          탭
│  └─ settings/                내 계정 · 팀 · 요금제
└─ (workbench)/p/[id]/         전체 화면 편집기
```

- 이 저장소의 셸은 이미 둘이다. 공개(`(site)`)와 대시보드(`(app)`). 워크벤치는 아직 그룹이 없고, 가까운 것은 대시보드 셸 안에서 판을
  넓히는 `ScreenFrame` 이다. 사이드바를 아예 없애야 하면 새 그룹을 세운다(`references/nextjs.md`).
- **audience 가 바뀌면 그룹이 아니라 앱이 바뀐다**(루트 `CLAUDE.md` 「플랫폼 계층」). 판매자 스튜디오 · 운영팀 콘솔처럼 인증과 데이터
  범위가 통째로 다르면 새 앱이다.
- 작업 공간을 주소에 둘지(`/[ws]/…`)는 비싼 결정이다. 이 저장소는 들어온 조직을 행위자가 들고 다니고(INV-ACCESS-02) 주소에 두지 않는다.
  한 사람이 여러 조직을 하루에도 오가는 제품이면 지도에 `[ws]` 를 넣고 `spec-by-test` 로 행위자 세우기부터 바꾼다.

## 5. 화면의 상태는 주소에 담는다

| 상태 | 담는 곳 | 까닭 |
|---|---|---|
| 상세 · 무거운 탭 | 경로 세그먼트(`/[id]/analytics`) | 탭마다 데이터를 따로 읽고, 공유와 뒤로 가기가 탭을 기억한다 |
| 가벼운 탭 · 보기 방식 | 쿼리(`?tab=` · `?view=`) | 같은 데이터를 다르게 그릴 뿐이다 |
| 거름 · 정렬 · 검색어 · 쪽 | 쿼리(`?q=&sort=&page=`) | 공유 · 새로 고침이 같은 화면을 연다 |
| 고른 항목 · 열린 시트 | 쿼리(`?selected=`) 또는 가로챈 라우트 | 링크 하나로 남도 같은 화면을 본다 |
| 펼침 · 마우스 올림 · 입력 중인 글 | 브라우저 상태 | 남에게 보낼 일이 없다 |

- 거름을 바꿀 때는 `replace` 로 고친다. 뒤로 가기가 거름 하나하나를 되감으면 안 된다. 상세로 들어가는 이동만 `push` 다.
- **가로챈 라우트 + 병렬 라우트**를 함께 쓰면 목록에서 누를 때는 다이얼로그 · 시트로 열리고, 링크로 바로 오면 전체 페이지로 열린다.
  Figma · v0 의 공유 링크가 퍼지는 원리와 같다. 짓는 법은 `references/nextjs.md` 에 있다.
- 주소는 `lib/paths.ts` 하나가 만든다. 쿼리도 `withQuery` 를 지난다.

## 6. 다시 오게 만드는 장치

대시보드의 홈 · 사이드바 · 받은 것에서 이 장치들이 어디에 서는지는 `references/dashboard.md` 2 · 3 · 9번에 있다.

- **홈은 「이어 하기」다.** 최근 프로젝트 · 최근에 본 채널 · 내가 처리할 것을 맨 위에 둔다. 환영 문구와 기능 소개를 두지 않는다.
- **빈 상태는 온보딩이다.** 빈 목록에 만들기 단추와 템플릿(또는 본보기 하나)을 세운다.
- **모든 결과물에 공유 주소가 있다.** 공유 링크가 새 사용자가 들어오는 길이다. 공유된 화면은 로그인하지 않은 사람에게 무엇을 보이는지 정한다.
- **저장과 컬렉션.** 분석 · 탐색 도구를 다시 찾게 만드는 가장 큰 까닭이다.
- **역할별 보기.** 「내 근무」와 「구성원 관리」처럼 같은 객체를 역할마다 다르게 보인다. 역할로 메뉴를 거르는 판정은 화면이 아니라
  도메인 술어에 둔다(지금 `NavEntry` 는 역할로 거르지 못한다. 필요하면 셸을 늘리는 일이 지도에 들어간다).
- **사이드바의 객체 메뉴는 다섯에서 일곱이다.** 개인 묶음(홈 · 받은 것 · 내 일)과 맨 아래의 설정 한 줄은 따로 센다. 새 기능은 거름 · 탭 ·
  설정 · CTA 로 흡수한다. 여덟째 객체 메뉴가 필요하다는 것은 2번을 다시 할 때라는 뜻이다.

## 7. 검증한다

- **루프의 클릭 수.** 1번의 예산을 e2e 로 잰다. 홈에서 시작해 루프를 끝내는 스펙 하나를 두고 클릭을 센다(`references/nextjs.md`).
  예산을 넘으면 스펙이 빨개진다. IA 의 회귀를 막는 유일한 기계다.
- **트리 테스트.** 「X 는 어디에 있을까요?」 질문 다섯 개로 사람(또는 이 대화를 모르는 서브에이전트)이 메뉴만 보고 찾는지 본다.
  답과 찾은 길을 적는다.
- **출시 뒤 경로.** PostHog 의 경로 분석으로 루프의 어디서 떠나는지 본다(분석 모듈이 있을 때).
- `node .claude/skills/ia-design/scripts/routes.mjs` 로 지금의 라우트 나무를 찍는다. 깊이가 셋(목록 → 상세 → 탭)을 넘는 주소와 메뉴의 줄 수를 알린다.

## 산출물

확인받을 때 다음을 한 묶음으로 보인다. 지도는 문서로 남기지 않고, 다 지은 뒤에는 라우트 디렉터리와 e2e 가 답한다
(`spec-by-test` 「다 만든 뒤」). 남길 만한 판단만 `docs/decisions/` 에 적는다.

| 묶음 | 꼴 |
|---|---|
| 꼴 | 관리형 · 생성형 · 탐색형 가운데 무엇이 섞였나 |
| 루프 | 역할마다 한 줄 + 클릭 예산 |
| 객체 | ORCA 표(누가 보나 칸 포함) |
| 라우트 나무 | 4번의 나무 모양. 셸(그룹)마다 묶는다 |
| 그릇 | 객체 · 동작마다 3번 표의 어느 줄인가, 왜인가 |
| 주소 상태 | 5번 표를 이 제품으로 채운 것 |
| 메뉴 | 셸마다 개인 묶음 · 객체 다섯에서 일곱 · 맨 아래, 역할마다 다르면 역할마다 |
| 검증 | 루프 e2e 의 이름과 트리 테스트의 질문 다섯 |
