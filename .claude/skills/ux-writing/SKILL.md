# 화면의 글

화면의 글은 읽히는 글이 아니라 **훑이고 눌리는 글**이다. 사람은 문장을 읽지 않고 단어를 짚으며 지나가고,
그 사이에 무엇을 누를지 정한다. 그래서 이 스킬의 기준은 하나다.

> **이 글이 없으면 사람이 무엇을 놓치는가.** 답할 수 없으면 그 글은 넣지 않는다.

기본값은 **없음**이다. 글은 있어야 할 까닭이 있을 때만 선다. 자리가 비어 보인다는 것은 까닭이 아니다.

토스의 라이팅 원칙(코어밸류 Clear · Concise · Casual · Respect · Emotional 과 8원칙)과 개발자센터의 문체 규칙을
뼈대로 삼고, 에이전트가 코드를 짜며 화면을 만들 때 생기는 버릇을 막는 조항을 더했다. 예시는
`references/examples.md` 에 있고 **규칙과 예시를 함께 읽는다.**

## fluent-korean 과 무엇이 다른가

| | `fluent-korean` | `ux-writing` |
|---|---|---|
| 대상 | 문서 · PR · 주석 · 보고. 사람이 **읽는** 글 | 화면 · 알림 · 메일. 사람이 **훑고 누르는** 글 |
| 문체 | 평서체(~다) 또는 합쇼체 | **해요체**(~요) |
| 길이 | 까닭을 충분히 적는 것이 미덕 | 없어도 되는 말을 빼는 것이 미덕 |
| 독자 | 이 저장소를 만지는 사람 | 이 저장소를 **모르는** 사람 |

둘을 섞지 않는다. 주석에 적을 까닭을 화면으로 올리지 않고, 화면의 말투를 문서로 끌고 가지 않는다.

## 왜 에이전트의 화면 글이 길어지나

코드를 짜던 대화가 그대로 화면으로 흘러들기 때문이다. 에이전트는 방금 무엇을 만들었는지, 어떤 제약을 풀었는지,
어디가 아직 비어 있는지를 알고 있고, 그것을 사람에게도 알려 주고 싶어 한다. 그 결과가 이런 글이다.

- 기능을 **소개하는** 설명: 「에이전트와 나누는 대화는 끊겨도 이어집니다」
- 구현을 **변명하는** 설명: 「서버가 다시 떠도 대화가 남습니다」
- 개발 상태를 **보고하는** 글: 「아직 연결되지 않았어요」「준비 중인 기능입니다」「(예시)」
- 제목을 **되풀이하는** 설명: 제목 「쪽지」 아래 「쪽지를 관리하는 화면입니다」

화면을 쓰는 사람은 그 대화에 없었다. 그래서 글은 **코드가 다 선 다음 따로 한 번** 쓴다. 이 대화를 모르는 사람이
처음 이 화면을 연다고 보고, 그 사람이 지금 할 일에 필요한 말만 남긴다.

## 절차

화면 하나를 만들거나 고칠 때마다 이 차례를 지난다.

1. **글을 전부 뽑는다.** 제목 · 설명 · 단추 · 라벨 · placeholder · 도움말 · 빈 화면 · 오류 · 토스트 · 배지 ·
   툴팁 · aria-label 까지 한 줄에 하나씩 적는다. 보이지 않는 aria-label 도 글이다.
2. **하나씩 없애 본다.** 각 줄에 아래 「넣는 기준」의 세 물음을 던진다. 하나도 「예」가 아니면 지운다.
3. **남은 것을 겹치지 않게 한다.** 한 화면에서 같은 말은 한 번만 선다. 제목이 말한 것을 설명이 다시 말하지 않고,
   라벨이 말한 것을 placeholder 가 다시 말하지 않는다.
4. **개발의 말을 걷는다.** 아래 「개발의 말」 목록과 대조한다.
5. **문체를 맞춘다.** 아래 「문체」를 적용한다.
6. **소리 내어 읽는다.** 입으로 읽어 어색하면 고친다. 눈으로 읽어 괜찮은 것과 다르다(Easy to speak).
7. **다음 화면을 예상할 수 있는지 본다.** 단추를 누르면 무슨 일이 일어나는지 단추의 글만 보고 알 수 있어야 한다
   (Predictable hint).
8. **새 눈에게 맡긴다.** 서브에이전트 `ux-writing-reviewer`(`.claude/agents/ux-writing-reviewer.md`)를 부른다. 넘기는 것은
   **볼 범위뿐이다**(파일 · 라우트 · "이번 변경"). 왜 그렇게 만들었는지는 넘기지 않는다. 그 에이전트는 이 대화를 모르는
   사람의 자리에서 화면을 읽고, 고칠 글을 표로 돌려준다. 고치는 일은 부른 쪽이 한다.

⚠ **1~7 을 건너뛰고 8 만 하지 않는다.** 검토자는 두 번째 눈이지 첫 번째 눈이 아니다. 만든 쪽이 먼저 걷어 내야
   검토가 판단이 갈리는 자리에 시간을 쓴다.

## 넣는 기준

글 하나마다 묻는다. **셋 가운데 하나라도 「예」여야** 그 글이 선다.

1. **이 글이 없으면 사람이 다음에 할 일을 모르는가.** (단추 · 빈 화면의 다음 걸음 · 오류의 해결 방법)
2. **이 글이 없으면 사람이 틀린 것을 누르거나 잃는가.** (지우기 확인 · 되돌릴 수 없는 일 · 공개 범위)
3. **이 글이 없으면 지금 상태를 모르는가.** (진행 · 완료 · 실패 · 비어 있음)

아래는 대개 셋 다 「아니요」다. 넣기 전에 한 번 더 묻는다.

- 페이지 제목 아래의 설명. 제목과 화면이 이미 말하는 경우가 대부분이다.
- 섹션마다 붙는 부제.
- 「~할 수 있어요」로 기능을 소개하는 문장. 사람은 화면을 보고 안다.
- 폼 위의 안내문. 라벨이 충분하면 필요 없다.
- 입력칸이 무엇인지를 되풀이하는 placeholder. placeholder 는 **형식의 예**(`예: 2026-10-01`)가 필요할 때만 쓴다.
- 성공을 알리는 토스트. 화면이 이미 바뀌어 결과가 보이면 필요 없다.
- 아이콘 옆의 글. 뜻이 분명한 아이콘은 툴팁과 aria-label 로 충분하다(없애고 되돌리는 동작은 아이콘이 기본이다).

⚠ **친절은 설명의 양이 아니다.** 모든 맥락을 알려 주는 것만 친절한 게 아니라, 지금 필요한 것만 남기는 것이 더
친절하다(Focus on key message). 만드는 사람의 불안 때문에 설명을 더하지 않는다.

## 개발의 말

화면에 서면 안 되는 말이다. 만든 사람만 아는 말이고, 쓰는 사람에게는 소음이거나 불안이다.

| 갈래 | 예 | 대신 |
|---|---|---|
| 구현 · 인프라 | 서버 · DB · API · 스키마 · 캐시 · 토큰 · 워크플로 · 스텝 · 훅 · 큐 · 세션 · 스트림 · 모델을 부르다 | 사람이 겪는 결과로 말한다(「저장했어요」「다시 불러오는 중이에요」) 또는 지운다 |
| 식별자 · 코드 값 | `id=1234` · `wrun_…` · `null` · `undefined` · enum 값(`archived` · `operator`) · 영문 상태 코드 | 사람이 부르는 이름(제목 · 날짜)과 우리말 상태 |
| 개발 상태 | 준비 중 · 미구현 · TODO · 임시 · 테스트용 · 예시 · 더미 · 연습 모드 · (beta) | 없는 기능은 화면에 세우지 않는다. 세웠으면 쓸 수 있어야 한다 |
| 내부 조직의 말 | 테넌트 · 멤버십 · 행위자 · 권한 판정 · 스코프 · 레코드 · 엔티티 · 트랜잭션 | 조직 · 멤버 · 나 · 볼 수 있는 사람 · 항목 |
| 오류의 원문 | 스택 · 예외 이름 · `permission denied` · `NotAppMember` · HTTP 코드 | 무슨 일이 있었고 무엇을 하면 되는지 한 줄 |
| 설계의 변명 | 「끊겨도 이어져요」「서버가 다시 떠도」「실시간으로 동기화돼요」 | 그 성질이 사람의 행동을 바꿀 때만, 사람의 말로 한 번 |

⚠ **로그와 오류 객체의 문구를 화면에 그대로 싣지 않는다.** 서버의 사유(「org.account 에 행이 없다」)는 서버 기록에
남고, 화면은 사람이 할 수 있는 일을 말한다(「초대받은 계정으로 다시 로그인해 주세요」).

## 모델이 읽는 글은 대상이 아니다

도구의 설명 · 시스템 프롬프트 · MCP 프로토콜의 설명은 **모델이 읽는 글**이다. 모델에게 정확히 일을 시키는 것이
목적이라 평서체와 식별자(`list_my_notes`)가 맞다. 이 스킬로 고치지 않는다.

⚠ **도구의 답은 화면 글이다.** 도구가 돌려준 문장은 모델이 거의 그대로 사람에게 옮긴다. 식별자와 오류 원문을 싣지 않고,
사람이 부르는 이름과 해요체로 쓴다.

한 파일이 통째로 모델이 읽는 글이면 머리(첫 40줄 안)에 `ux-writing-file: 까닭` 을 적어 기계 검사에서 뺀다.
화면 글과 섞인 파일은 줄 끝의 `// ux-writing: 까닭` 을 쓴다. 까닭이 없으면 빼지 않는다.

## 문체

토스 개발자센터의 규칙을 따른다.

1. **해요체.** 제목 · 버튼 · 라벨처럼 문장이 아닌 것을 빼고 모든 문장은 「~해요」로 맺는다. 합쇼체(~습니다)와 섞지 않는다.
2. **능동형.** 「저장되었습니다」가 아니라 「저장했어요」. 누가 했는지가 분명하면 능동으로 쓴다.
   예외: 서비스 종료 · 기간 만료처럼 주어를 강조해야 할 때만 수동형(「기간이 끝났어요」가 어색하면 「만료됐어요」).
3. **'~었' 빼기와 짧은 동사.** 「되었어요」→「됐어요」, 「불러와졌어요」→「불러왔어요」.
4. **긍정형.** 「~할 수 없어요」보다 「~하면 ~할 수 있어요」. 못 하는 이유보다 할 수 있는 길을 먼저 말한다.
5. **캐주얼한 경어.** 「~시겠어요?」「~하시나요?」「~께」「계시다」「여쭈다」를 쓰지 않는다.
   「삭제하시겠어요?」→「삭제할까요?」, 「고객님께」→「고객에게」. 빼서 어색하면 알고 싶은 것을 주어로 다시 쓴다.
6. **명사 나열 풀기.** 「비밀번호 재설정 요청 완료」→「비밀번호를 다시 정할 수 있게 메일을 보냈어요」. 한자어 명사는
   동사로 푼다(「진행」→「하는 중」, 「확인 필요」→「확인해 주세요」).
7. **권유하되 강요하지 않는다.** 「지금 안 하면 손해예요」「반드시」「즉시」처럼 겁을 주지 않는다(Suggest than force).
8. **영문 뒤 조사는 붙여 쓴다.** 「Claude에」「Scaffold를」. 저장소의 문서와 주석은 영문과 조사를 띄어 쓰지만(`packages/ui` 의),
   화면에서는 띄어 쓰면 읽다가 걸린다.
9. **모두가 아는 말.** 유행어 · 은어 · 업계 약어를 쓰지 않는다(Universal words). 영어는 사람들이 실제로 그렇게 부를
   때만 쓴다(「로그인」은 되고 「어센티케이션」은 안 된다).
10. **감정이 걸린 순간을 놓치지 않는다.** 처음 완료 · 오래 걸린 일의 끝 · 실패한 뒤처럼 사람이 무언가를 느끼는 자리에서는
   정보에 한마디를 더해도 된다(Find hidden emotion). 그 밖의 자리에는 더하지 않는다.

## 자리별 규칙

| 자리 | 규칙 |
|---|---|
| **버튼** | 누르면 일어나는 일을 **동사**로. 「{대상} {동사}」 두 마디 안(「쪽지 쓰기」「기록 보기」「연결 끊기」). 「확인」「예」처럼 무엇을 하는지 모르는 말은 피한다. 마침표 없음 |
| **다이얼로그 버튼** | 왼쪽(물러서기)은 **「닫기」**로 통일한다. 「취소」는 하던 일이 취소된다고 오해한다. 오른쪽은 제목의 동사를 그대로(제목 「쪽지를 지울까요?」→ 버튼 「지우기」) |
| **페이지 제목** | 명사 하나나 짧은 명사구. 마침표 없음. 설명은 기본으로 두지 않는다 |
| **라벨** | 명사. 「이름」「공개 범위」. 콜론 · 마침표 없음. 필수 표시는 모양(*)이 아니라 선택 항목에 「(선택)」을 다는 쪽이 대개 짧다 |
| **placeholder** | 형식의 예가 필요할 때만 「예: …」. 라벨을 되풀이하지 않는다. placeholder 에 설명을 넣지 않는다(입력하면 사라진다) |
| **도움말** | 틀리기 쉬운 것 하나만. 두 줄을 넘으면 입력칸을 다시 설계한다 |
| **빈 화면** | 무엇이 비었는지 한 줄 + 다음에 할 일 단추 하나. 「아직 쪽지가 없어요」+「쪽지 쓰기」. 기능 소개를 붙이지 않는다 |
| **오류** | 무슨 일인지 + 무엇을 하면 되는지. 사람을 탓하지 않는다(「잘못 입력했어요」가 아니라 「이메일 형식을 확인해 주세요」). 오류 코드는 지원에 필요할 때만 작게 |
| **확인 창** | 되돌릴 수 없을 때만 띄운다. 제목은 질문 하나(「쪽지를 지울까요?」), 본문은 잃는 것이 있을 때만(「지운 쪽지는 되살릴 수 없어요.」) |
| **토스트** | 화면에서 결과가 보이지 않을 때만. 「~했어요」 한 문장. 되돌릴 수 있으면 「되돌리기」 단추를 함께 |
| **배지 · 상태** | 우리말 한두 단어(「보관됨」「진행 중」「완료」). 상태 어휘는 앱마다 한 파일에 모은다 |
| **aria-label · 툴팁** | 보이는 이름과 같은 말. 아이콘만 있는 단추에는 반드시 단다 |
| **알림 · 메일 제목** | 명사형이나 「~하기」, 마침표 없음. 본문은 해요체 문장과 마침표 |

## 숫자 · 날짜 · 부호

- 숫자는 아라비아 숫자로 쓰고 단위를 붙인다(「3개」「2시간」). 큰 금액은 세 자리마다 쉼표.
- 날짜는 화면 안에서 한 모양으로 통일한다(포매터 하나를 지난다. 금액과 비율은 `@investment/schema` 의 `formatWon` · `formatPercent` 다). 가까운 날은 「오늘」「어제」가 더 빠르다.
- 문장이 아닌 것(제목 · 버튼 · 라벨 · 배지)에는 마침표를 찍지 않는다. 문장인 설명 · 오류 · 토스트에는 찍는다.
  한 화면 안에서는 섞지 않는다.
- 느낌표와 이모지는 감정이 걸린 순간(첫 완료 등)에만, 한 화면에 하나까지.
- 따옴표 · 괄호로 강조하지 않는다. 강조가 필요하면 문장을 줄인다.

## 끝나기 전에

- [ ] 화면의 글을 전부 뽑아 한 줄씩 「없으면 무엇을 놓치나」를 물었다
- [ ] 제목과 설명, 라벨과 placeholder 가 같은 말을 되풀이하지 않는다
- [ ] 개발의 말(구현 · 식별자 · 개발 상태 · 내부 조직의 말 · 오류 원문)이 없다
- [ ] 모든 문장이 해요체이고 능동형 · 긍정형이다. 「~시겠어요」「되었습니다」가 없다
- [ ] 버튼은 동사이고, 누르면 무슨 일이 일어나는지 버튼만 보고 안다
- [ ] 다이얼로그의 물러서는 버튼은 「닫기」다
- [ ] 소리 내어 읽어 어색한 곳이 없다
- [ ] 기계 검사를 돌렸다: `node .claude/skills/ux-writing/scripts/scan-copy.mjs apps/web/src/app apps/web/src/components`
- [ ] `ux-writing-reviewer` 에게 범위만 넘겨 검토받고, 받은 표를 반영했다(e2e 의 단언도 함께)

⚠ **기계 검사는 글자로 드러나는 것만 잡는다.** 「이 글이 필요한가」는 사람이 판단한다. 검사가 조용하다고 화면이
좋다는 뜻은 아니다.
