# 모듈을 나중에 붙인다

모듈은 스캐폴드 원본의 `modules/<이름>/` 에 있다. 모듈 파일 넷은 다음과 같다.

| 파일 | 담는 것 |
|---|---|
| `module.md` | 무엇을 하는 모듈인가 |
| `owns.json` | 이 모듈만 갖는 자리와 의존 |
| `wiring.md` | 코어에 잇는 자리와 그 뜻 |
| `acceptance.json` | 붙인 뒤 지나야 할 검사 |

붙이는 일은 둘로 나뉜다.

- **기계식 반쪽(스크립트).** 원본에서 이 프로젝트와 같은 이름 · 포트로 「모듈 없음」과 「모듈 있음」을 새로 찍는다. 그 차이를
  파일마다 옮긴다. 이름과 포트는 이미 이 프로젝트의 것이다.
- **판단(너).** 프로젝트가 원본에서 갈라진 자리에서는 패치가 붙지 않는다. 그 자리를 `wiring.md` 의 뜻대로 잇는다.

## 차례

### 1. 준비

- `scaffold.json` 을 읽는다. 원본 경로(`source`)와 이름 · 포트 · 켠 모듈이 있다.
  - 파일이 없으면 이 기능 전에 만든 프로젝트다. 다음 값을 찾아서 5번의 스크립트에 플래그로 준다.

    | 값 | 찾는 곳 |
    |---|---|
    | 이름 | `package.json` 의 스코프 |
    | 화면 이름 | 앱의 `metadata` |
    | 앱 포트 | `apps/web/package.json` 의 `-p` |
    | DB 대역 | `supabase/config.toml` 의 `[api] port` 에서 끝자리를 뗀 값 |
    | 켠 모듈 | `modules/` 아래의 폴더 |

  - 원본 경로를 모르면 사람에게 묻는다.
- 원본 저장소에 원격이 있으면 `git -C <source> pull` 을 먼저 한다.
- 원본의 `modules/<모듈>/module.md` 와 `wiring.md` 를 읽는다. **무엇이 붙는지 사람에게 한 문단으로 말하고 나서** 시작한다.
- `requires` 에 있는 모듈이 아직 없으면 그것부터 붙인다.
- `scaffold.json` 의 `adopted` 에 있는 모듈은 `/scaffold-fit` 이 제품 코드로 편입한 것이다. 스크립트가 멈추고, 그 코드는 제품의 코드로 직접 고친다.

### 2. 작업 트리를 깨끗하게 한다

- `git status` 가 비어 있어야 한다. 스크립트는 깨끗하지 않으면 멈춘다. 되돌릴 길을 남기려는 것이다.
- 사람이 하던 일이 남아 있으면 **커밋하거나 치워 달라고 묻는다.** 너 마음대로 stash 하거나 커밋하지 않는다.

### 3. 기계식 반쪽을 돌린다

```bash
node <source>/scripts/module-patch.mjs add <모듈> --project .
```

끝나면 결과를 다섯 가지로 알려 준다.

| 결과 | 뜻 |
|---|---|
| 복사한 파일 | 모듈이 가진 자리. 대개 전부 여기다 |
| 패치가 붙은 파일 | 표시 줄 · 의존 · 문서 줄이 제자리에 들어갔다 |
| **붙지 않은 조각** | 파일 옆에 `.rej` 가 남았다. 4번에서 푼다 |
| 이미 있는데 내용이 다른 파일 | 건드리지 않았다. 같은 이름의 다른 것인지 보고, 합칠지 사람에게 묻는다 |
| 마이그레이션이 더 늦은 것보다 앞선다 | 4번에서 판단한다 |

### 4. 붙지 않은 자리를 푼다

`wiring.md` 의 「표시 줄」 표와 「판단이 드는 자리」를 옆에 두고 한다.

- **`.rej` 조각.**
  - 조각이 넣으려던 줄(`+`)을 그 파일의 같은 뜻의 자리에 넣는다. 표시 줄(`scaffold:module <모듈>`)은 그대로 달고 온다.
  - 넣은 뒤 `.rej` 를 지운다.
  - 같은 자리가 없어졌으면(프로젝트가 구조를 바꿨으면) 그 파일의 지금 모양에서 같은 일을 하는 자리를 찾는다. 찾지 못하면 멈추고 묻는다.
- **마이그레이션의 순서.**
  - 프로젝트의 마이그레이션이 원격 DB 에 이미 올라갔다면 모듈의 마이그레이션 이름을 프로젝트의 마지막 것보다 늦은 시각으로 바꾼다.
  - 아직 로컬뿐이면 그대로 둬도 된다. 어느 쪽인지 모르면 묻는다.
- **시드의 id.** 모듈의 시드가 쓰는 id(테넌트 · 계정 · 멤버십)가 프로젝트의 시드와 겹치는지 본다. 겹치면 빈 id 로 바꾼다.
- **문서.**
  - 루트와 앱의 `CLAUDE.md` 에 모듈의 줄이 들어갔는지 본다(`owns.json` 의 `docs`).
  - 프로젝트가 문서를 고쳐 써서 패치가 붙지 않았으면, `wiring.md` 의 「문서」 표를 보고 같은 뜻의 자리에 적는다.
- **스킬.** `owns.json` 의 `skills` 는 복사로 들어왔다. `skills-lock.json` 에 항목이 없으면 `wiring.md` 의 명령으로 다시 받는다.

**손대지 말 것**
- **코어의 코드를 모듈에 맞춰 고치지 않는다.** 모듈은 확장 지점을 채울 뿐이다.
- 확장 지점 자체가 프로젝트에 없으면(원본보다 오래된 코어) 멈추고 알린다. 코어부터 원본에 맞추는 것은 다른 일이다.

### 5. 설치하고 검사한다

```bash
npm install
supabase db reset
```

그 뒤 `modules/<모듈>/acceptance.json` 의 검사를 모두 돌린다. 차례는 `checks` → `unit` → `contract` → `e2e` 다.

- `contract` 와 `e2e` 는 로컬 스택이 떠 있어야 한다(`needs`).
- 개발 서버가 같은 포트에 떠 있으면 e2e 전에 내려 달라고 말한다.
- 코어의 검사(`npx turbo typecheck test` · web e2e 전체)도 돌린다. 붙인 모듈이 코어를 깨지 않았는지 보는 것이다.

### 6. 보고한다

- 스크립트가 옮긴 것은 개수만 말한다.
- **판단한 자리는 하나씩 적는다.** 파일, 무엇을 했나, 왜 그렇게 했나.
- 검사 결과를 적는다.
- 사람이 할 일(키 · 대시보드 등)은 `module.md` 의 「요구하는 것」에서 가져온다. 키는 사람이 터미널에서 `.env.local` 에 넣는다.
- 커밋은 사람이 하라고 할 때 책임별로 나눠서 한다(모듈의 자리 · 코어에 잇는 줄 · 문서). `scaffold.json` 은 잇는 줄과 함께 찍는다.
