# 팀 관리는 자기 테넌트 안의 일이고 web_app 에 컬럼 단위로 연다

## 정한 것

- 설정에 팀(`/settings/team`)과 내 계정(`/settings/account`)을 둔다. 지금 들어온 테넌트의 사람을 초대하고, 역할을
  관리자와 구성원 사이로 바꾸고, 내보낸다. 내 계정에서는 이름을 고친다.
- **자격은 새 불변식이다(INV-ACCESS-09).** 같은 테넌트의 소유주와 관리자만 관리하고 구성원은 목록만 본다. 운영 도구의
  자격(INV-ACCESS-05)과 **따로 세운다**(사용자 결정). 합치면 고객사의 소유주가 운영 도구를 여는 길이 생긴다.
- **소유주는 팀 관리로 바뀌지 않는다(INV-ACCESS-10).** 초대로 세우지 못하고, 역할을 바꾸거나 내보내지 못한다. 소유주
  넘기기는 이번에 넣지 않았다(사용자 결정).
- **쓰기 권한은 web_app 에 컬럼 GRANT 로 연다**(사용자 결정, 추천안). 계정 `email` · `name` INSERT · `name` UPDATE,
  멤버십 `account_id` · `tenant_id` · `role` INSERT · `role` · `active` UPDATE 다(`*_grant_team_writes.sql`).
  행 판정은 유스케이스가 부르는 계획 함수가 하고, 쓰는 문장이 조건(바꾸기 전 역할 · 살아 있는 멤버십 · 소유주가 아님)을
  한 번 더 건다. 쪽지와 같은 모양이다.
- **초대 메일은 보내지 않는다**(사용자 결정: 나중에). 명부에 행을 세우면 그 주소의 Google 계정이 처음 로그인할 때
  이어진다(INV-ACCESS-08).
- 팀에서 빼기는 행을 지우지 않고 멤버십을 끊는다(INV-ACCESS-03). 다시 초대하면 같은 멤버십이 되살아나 되돌릴 수 있어서
  확인 창을 띄우지 않는다(사용자 결정. 검토자는 잘못 누르기 쉽다고 봤다).
- 화면 글 검토 뒤에 정한 것(사용자 결정):
  - 초대만 받고 아직 로그인하지 않은 사람(`auth_user_id` 가 빈 칸)에게 「초대됨」을 단다.
  - 나간 계정은 멤버십이 살아 있어도 팀 목록과 찾기에서 뺀다. 어느 조직에도 들어오지 못하는 사람이다.
  - 여러 조직에 속한 사람에게는 사이드바에 지금 조직의 이름을 적는다. 조직이 하나면 적지 않는다.
  - 화면의 역할 이름은 「소유자 · 관리자 · 멤버」이고 「내보내기」 대신 「팀에서 빼기」다. 코드와 불변식의 산문은 「소유주」 그대로다.

## 까닭

- 다른 길은 `security definer` 함수 하나로 쓰기를 모으는 것이었다. 판정이 SQL 에 한 번 더 서지만 규칙이 두 곳에
  생기고, 두 벌은 갈라진다. 이 저장소는 판정을 도메인 패키지의 순수 함수 하나에 두고 DB 는 경계(GRANT)만 갖는다.
- 넓어진 권한 가운데 되돌리기 어려운 것은 막아 두었다. 남의 주소를 바꾸거나 나간 사람을 살리지 못하고, 멤버십을 다른
  사람이나 테넌트로 옮기지 못하며, 테넌트에는 쓰지 못한다. `team-directory.postgres.test.ts` 가 롤마다 잰다.
- 이 결정으로 초기 스키마의 설명(「앱의 롤에는 컬럼 단위로 SELECT 만, 예외는 `auth_user_id` 하나」)이 예외 둘로 바뀌었다.
  `docs/개발-방법론.md` 와 `docs/supabase-migrations/README.md` 를 함께 고쳤고, 초기 마이그레이션의 주석은 적은 그대로 둔다.

## 실측

- 로컬에서 `seed.sql` 을 다시 돌리면 식별자 시퀀스가 1000 으로 돌아가 계약 검사가 만든 행과 부딪친다. 계정을 세우는
  문장의 `on conflict do nothing` 이 그 기본 키 충돌도 삼켜 「그사이 팀이 바뀌었어요」로 답했다. 시드를 다시 깔 때는
  `supabase db reset` 을 쓴다.
