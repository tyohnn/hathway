## 무엇을 정했나

advisor 는 `supabase-js`(PostgREST)를 쓰지 않고 `pg` 로 데이터베이스에 직접 붙습니다. 배포는 Vercel 서버리스이고 풀러는 **6543 트랜잭션 모드**를 씁니다. `legal` 스키마는 Data API 노출 목록(`supabase/config.toml` 의 `[api] schemas`)에서 뺍니다.

## 고려한 것

`legal.create_task` plpgsql 함수가 성격이 다른 두 가지를 묶고 있었습니다.

| 묶여 있던 것 | 판정 |
|---|---|
| 자문과 첫 열람권을 한 트랜잭션에 넣는 경계 | 정당합니다. 자문만 저장되고 열람권이 빠지는 상황은 막아야 합니다 |
| 담당자가 0명이면 거절하는 규칙(INV-LEGAL-03) | 정당하지 않습니다. 불변식의 소유자가 도메인 함수인데 저장소가 같은 규칙을 한 번 더 가지면 언젠가 두 판정이 어긋납니다 |

트랜잭션 경계는 두고 규칙만 걷어 내려면 앱이 트랜잭션을 직접 열어야 합니다. PostgREST 는 요청 하나가 트랜잭션 하나라서 그 수단이 없습니다.

## 고른 까닭과 결과

- **한 문장이 곧 하나의 트랜잭션입니다.** 자문 삽입과 열람권 삽입을 데이터 수정 CTE 로 묶었습니다. 왕복이 한 번으로 끝나고 업무 규칙은 도메인에 남습니다.
- **열람권 질의가 세 번에서 한 번으로 줄었습니다.** PostgREST 가 `assigner_id` 와 임베드된 `grant.admin_user_id` 를 `or` 로 묶지 못해 후보 id 를 두 갈래로 모으던 제약과 `in` 절 상한 문제가 함께 사라졌습니다.
- **HTTP 로 닿는 경로가 없습니다.** 「권한 판정은 서버 액션 안의 도메인 함수가 한다」는 접근 모델과 맞습니다.
- `date` 타입은 문자열 그대로 받도록 파서를 지정합니다. 기본 파서는 로컬 시간대의 `Date` 로 바꾸는데 마감일은 시각이 아니라 달력의 하루입니다.

## 서버리스 배포가 정한 규칙

| 축 | advisor |
|---|---|
| 풀러 포트 | 6543 트랜잭션 모드. 멈춘 인스턴스가 커넥션을 쥐고 있지 않게 합니다 |
| 풀 크기 | 인스턴스마다 `max: 3`. 실제 부하는 인스턴스 수에 max 를 곱한 값입니다 |
| 풀 수명 | `globalThis` 에 두어 재사용되는 인스턴스가 기존 풀을 씁니다 |

- ⚠ 트랜잭션 모드에서는 **이름을 붙인 prepared statement 를 쓰지 않습니다.** 뒤쪽 커넥션이 바뀌면서 「prepared statement does not exist」가 납니다. 트랜잭션 밖의 `set` · `listen` · 세션 수명 advisory lock 도 같은 이유로 쓰지 않습니다.
- ⚠ 로컬 Supavisor 로 실측한 결과, `statement_timeout` 과 `application_name` 을 **풀 설정**으로 주면 연결은 성공하지만 값이 전달되지 않습니다(실제 값은 `statement_timeout=0`, `application_name=Supavisor`). 시작 패킷을 풀러가 소비하기 때문입니다. **롤 설정**(`alter role … set`)으로 주면 전달됩니다. 그래서 어댑터의 풀 설정에서 두 값을 뺐습니다. 거부되지 않아서 적용되어 있다고 믿게 되는 것이 함정입니다.

## 놓아준 것

`supabase-js` 가 주던 타입 생성과 HTTP 캐시를 쓰지 않습니다. 전송(풀 · TLS · 트랜잭션)은 `packages/adapters-postgres/src/connection.ts` 한 곳이 소유합니다.

## 코드에서 지키는 자리

- `packages/adapters-postgres/src/connection.ts`
- `supabase/config.toml` 의 `[api] schemas`
