# 모듈은 코어의 확장 지점을 채우고 한 파일에서만 잇는다

## 정한 것

- hathway 를 **모듈을 골라 붙이는 모양**으로 만든다(사용자 아이디어). 만들 때(`create.sh --with`) 고르고, **나중에 붙이기도
  한다**(사용자 결정). 나중에 붙이는 일은 완전한 기계식이 어려우므로 에이전트가 모듈의 안내를 읽고 판단해 잇는다.
- 첫 모듈은 결제 · 분석(PostHog) · agent · MCP · 공개 화면이고, 아무것도 고르지 않으면 로그인 · 팀 · 설정 · 예시 도메인이
  남는다(사용자 결정).
- **코어는 확장 지점만 안다**(`apps/web/src/extensions/*`). 지금 둘이다.
  - `PlanLimits`: 조직이 무엇까지 쓰는가(멤버 한도 · MCP). 기본 구현은 한도 없음.
  - `CreditMeter`: AI 기능 하나를 재며 부르는가. 기본 구현은 부르기만 함.
- **모듈과 코어를 잇는 곳은 `apps/web/src/lib/modules.ts` 하나다.** 켠 모듈의 줄에 `scaffold:module <이름>` 을 달고, 모듈을
  떼는 일은 그 줄을 걷고 모듈이 가진 자리를 지우는 것이다. 남은 확장 지점은 기본 구현으로 돈다.
- **모듈이 가진 web 코드는 `apps/web/src/modules/<이름>/` 에 모은다.** 라우트처럼 자리를 옮길 수 없는 것만 `app/` 에 둔다.
- **`check:modules` 가 섞임을 막는다.** 모듈이 가진 자리 밖의 파일은 그 모듈의 패키지와 폴더를 import 하지 못한다.

## 순서(사용자 확인)

1. 확장 지점을 세우고 결제를 그 위로 옮긴다. ← 이 기록
2. 결제 모듈에 모듈 파일 넷(`module.md` · `owns.json` · `wiring.md` · 받아들임 검사)을 단다.
3. `create.sh --with` 와 CI 의 조합(모두 켬 · 모두 끔 · 하나씩 켬).
4. `/scaffold-add` · `/scaffold-remove` 스킬. 첫 시험은 결제를 뺀 프로젝트에 결제를 다시 붙이는 것이다.
5. PostHog 모듈을 처음부터 모듈로 세운다.
6. agent · MCP · 공개 화면을 모듈로 뗀다.

## 까닭

- 나중에 붙이려면 모듈이 코어의 여기저기에 들어가 있으면 안 된다. 프로젝트마다 코어가 갈라져서 기계식 패치가 깨지기
  때문이다. 코어가 확장 지점을 먼저 갖고 있으면 붙이는 일이 「모듈의 자리를 복사하고, 잇는 파일에 한 줄을 더한다」로 줄어
  에이전트가 판단할 자리가 작아진다.
- 기본 구현을 코어에 두는 까닭은 모듈이 없는 조립도 늘 도는 조립이어야 해서다. `extensions.test.ts` 가 결제 모듈 없이
  초대 · MCP · 요약이 도는 것을 잰다.
- 확장 지점을 web 앱 안에 둔 것은 쓰는 자리(팀 초대 유스케이스 · MCP 라우트 · 요약 유스케이스)가 모두 web 이기 때문이다.
  다른 앱이 같은 확장 지점을 쓰게 되면 그때 패키지로 내린다.

## 모듈 파일 (2단계)

모듈마다 `modules/<이름>/` 에 넷을 둔다. 결제는 `modules/billing/` 이다.

| 파일 | 무엇 | 누가 읽는가 |
|---|---|---|
| `module.md` | 무엇을 하는가 · 채우는 확장 지점 · 요구하는 것 | 사람과 에이전트 |
| `owns.json` | 모듈만 갖는 자리 · 패키지 · 의존성 · 스킬 · 환경값 | `check:modules` · 떼고 붙이는 일 |
| `wiring.md` | 코어에 잇는 자리. 표시 줄(기계식)과 판단이 드는 자리(에이전트) | 떼고 붙이는 일 |
| `acceptance.json` | 붙이거나 뗀 뒤 지나야 할 검사 | 떼고 붙이는 일 · CI |

- 코어 화면이 결제의 주소를 직접 알던 자리(「요금제 보기」 링크)는 확장 지점이 주소를 답하게 바꿨다
  (`PlanLimits.upgradeHref` · `Metered.topUpHref`). 결제의 경로와 메뉴는 모듈 폴더로 옮기고 `lib/moduleNav.ts` 가 잇는다.
- 코어 시드에 있던 고객사 C 와 그 소유자는 결제 모듈의 시드로 옮겼다. 코어의 MCP 스펙에 있던 무료 조직 테스트는 결제
  스펙으로 옮기고, 로그인 사슬은 `e2e/mcpConnect.ts` 로 뗐다.
- 코드가 아닌 잇는 자리(미들웨어 경로 · `next.config` · 검사 목록 · 환경값 · Playwright)에는 표시 줄을 달았다.
  `check:modules` 가 표시가 있는 모듈을 가리키는지, 그 파일이 `wiring.md` 에 적혀 있는지 잰다.
- 판단이 드는 자리(CLAUDE.md 의 표 · package.json · 스킬 잠금)는 `wiring.md` 가 절마다 적는다.

## 고르기와 조합의 검사 (3단계)

- `create.sh --with <모듈,…>|none` 이 고르지 않은 모듈을 걷는다. 가진 자리를 지우고, 표시 줄과 블록을 걷고, package.json 의
  의존 · 스킬 잠금 · 문서의 줄(`owns.json` 의 `docs`)을 뺀다. 원본의 모양을 알고 하는 일이라 기계식이다.
- 문서의 표와 문장은 줄 단위로 떼어지게 고쳐 썼다(결제의 문장이 다른 문장과 한 줄에 섞이지 않게). `check:modules` 가
  `docs` 의 줄이 그 문서에 꼭 한 번 있는지 잰다.
- 이름 바꾸기가 `scaffold:module` 표시까지 바꾸지 않게 비켜 둔다. 켠 모듈의 표시는 새 프로젝트에서도 그대로다.
- 코어의 코드가 주석에서도 `modules/<이름>/` 과 모듈의 불변식(`owns.json` 의 `invariants`, 결제는 `INV-BILLING`)을
  가리키지 않게 했다(`check:modules` 8번). 떼면 가리킬 곳이 사라진다. 「모두 끔」 프로젝트를 만들어 보니 코어의 주석 셋이
  `INV-BILLING-*` 를 인용해 `check:invariants` 가 「미정의」로 걸렸다. 그 모듈의 표시 줄은 함께 걷히므로 셈하지 않는다.
- 검사는 비밀을 담는 `.env*` 를 보지 않는다. `.env.example` 을 복사한 로컬 파일에도 표시 줄이 있어서다.
- CI 에 조합 잡(`modules`)을 더했다. 원본 잡이 「모두 켬」이고, 조합 잡이 나머지(지금은 「모두 끔」)를 만들어 타입체크 ·
  테스트 · 빌드를 돌린다. 모듈이 늘면 matrix 에 줄이 는다.


## 나중에 붙이고 떼기 (4단계)

- **기준 둘을 새로 찍어 그 차이를 옮긴다**(`scripts/module-patch.mjs`). 프로젝트를 만든 설정으로 원본에서 「모듈 없음」과
  「모듈 있음」을 `create-project.mjs` 로 찍으면, 둘의 차이가 곧 그 모듈이 그 프로젝트에 가져올 변화다. 이름 · 포트는
  이미 그 프로젝트의 것이라 따로 바꿀 일이 없다. 붙이는 일과 떼는 일이 같은 코드의 방향만 다르다.
- 차이는 파일마다 옮긴다. 새 파일은 복사하고, 사라지는 파일은 지우고, 고치는 파일은 `git apply --reject` 로 붙인다.
  붙지 않은 조각은 `.rej` 로 남기고, 에이전트가 `wiring.md` 를 보고 푼다(스킬 `/scaffold-add` · `/scaffold-remove`).
- **만든 설정은 새 저장소의 `scaffold.json` 에 적는다**(원본 경로 · 원본 커밋 · 이름 · 화면 이름 · 포트 · 켠 모듈).
  그 전에 만든 프로젝트는 스크립트에 플래그로 준다.
- 작업 트리가 깨끗해야 돈다. 지우고 고친 것을 git 으로 되돌릴 수 있게 하려는 것이다. 스크립트도 스킬도 사람의 변경을
  stash 하거나 커밋하지 않는다.
- 이름 바꾸기가 스킬 이름(`scaffold-add` · `scaffold-remove`)과 `scaffold.json` 도 비켜 간다. 바꾸면 새 프로젝트의 문서가
  `/<이름>-add` 같은 없는 스킬을 가리킨다(첫 시험에서 찾음).
- 버린 안: 원본의 `strip` 을 프로젝트에 직접 돌리기. 떼는 쪽은 되지만 붙이는 쪽을 못 한다. 붙이려면 이름 · 포트를 바꾼
  모듈의 파일이 있어야 하고, 그것을 만드는 가장 확실한 길이 `create-project.mjs` 를 다시 부르는 것이다.

## PostHog 모듈을 위한 사용자 결정 (2026-09-30)

조사(wizard 는 TTY · 브라우저 로그인이라 서브에이전트가 돌리지 못함, `posthog-for-claude` 는 보관됨) 뒤에 정했다.

- 4단계를 먼저 하고 PostHog 는 그다음이다.
- LLM 호출의 입력과 출력은 PostHog 에 기록하지 않는다(`recordInputs` · `recordOutputs` 끔). 쪽지 본문이 밖으로 나가지 않는다.
- Messaging(Workflows)은 나중이다. 수신자로 이메일을 PostHog 에 보내야 해서 「identify 는 계정 id 로만」과 부딪힌다.
- 동의는 쿠키 없는 모드(`cookieless_mode: "on_reject"`)다. 거절한 사람도 쿠키 없이 센다.
- 서버에서 보내는 이벤트도 동의한 사람의 것만 보낸다(2026-09-30 사용자 결정). 서버는 브라우저와 같은 동의 쿠키를 읽는다.
- 빌더 서브에이전트에 조각을 맡기지 않고 한 흐름에서 직접 만든다(2026-09-30 사용자 결정). 확장 지점과 브라우저 쪽 잇는 파일,
  동의의 설계가 조각마다 이어져서다.

## PostHog 모듈의 첫 조각: 분석 (5단계)

- **코어에 확장 지점 `ProductEvents` 를 더했다.** 액션의 ⑥(밖으로)에서 `capture(actor, 이벤트, 속성)` 을 부르고, 기본 구현은
  아무것도 하지 않는다. 오류 채널이 없다. 분석 때문에 사람의 일이 실패하면 안 된다. 유스케이스가 아니라 액션에서 부르는 것은
  ⑥이 밖으로 나가는 일의 자리이고, MCP 처럼 동의를 물을 수 없는 길이 유스케이스를 함께 지나기 때문이다.
- **브라우저 쪽 잇는 파일을 하나 더 두었다**(`lib/moduleClient.ts`, `check:modules` 의 `WIRING` 셋째). `lib/modules.ts` 는 서버
  전용이라 클라이언트 컴포넌트를 부를 수 없다. 코어가 자리 셋(모든 화면 · 로그인한 셸 · 로그인 화면)을 내놓고 그리는 일은
  `app/_components/ModuleSlots.tsx` 가 한다. 로그인한 사람은 id 두 개로만 건넨다.
- **동의의 정본은 우리 쿠키(`analytics_consent`)다.** posthog-js 는 동의를 브라우저 저장소에 두어 서버가 읽지 못한다. 서버의
  이벤트까지 동의로 거르려면 서버가 읽을 수 있는 자리가 정본이어야 한다. posthog-js 에는 그 값으로 opt-in · opt-out 을 알린다.
- 판정(동의 · 이벤트 카탈로그 · 계정 id 로만)은 새 도메인 패키지 `packages/analytics` 의 순수 함수 `planCapture` 가 하고,
  `INV-ANALYTICS-01~04` 가 그 규칙이다. posthog-node 는 `packages/adapters-posthog` 에만 있다.
- 서버는 `captureImmediate` 를 `after()` 안에서 부른다. 쌓았다 보내는 모양은 서버리스에서 응답 뒤에 버려지고, 곧바로
  보내면서 기다리면 응답이 늦는다. SDK 의 다시 보내기 기본값(3번 · 3초 · 10초 제한)은 함수 하나를 40초 붙잡아서 1번 · 0.5초 ·
  3초로 줄였다(시험에서 5초 시간 초과로 찾음).
- 키 없이 도는 연습 창구를 두었다(`NEXT_PUBLIC_POSTHOG_SINK=rehearsal`). 서버는 메모리에 모으고 `/api/analytics/rehearsal`
  로 내보이며, 브라우저는 `window.__rehearsalAnalytics` 에 모은다. e2e 가 실물 PostHog 없이 동의를 단언한다.
- `/ingest` 를 PostHog 로 넘기고(`next.config.ts` 의 `rewrites`), 미들웨어가 그 길을 로그인으로 돌리지 않게 했다. 돌리면
  로그인하지 않은 방문자의 이벤트가 `/login` 으로 가서 조용히 사라진다. 미들웨어의 `matcher` 는 글자 하나라 표시 줄을 달 수
  없어서, 함수 첫 줄에 표시 줄로 비켜 간다.
- 동의 배너는 오른쪽 아래의 작은 판이다. 왼쪽 아래는 사이드바의 계정 자리(로그아웃)다.
