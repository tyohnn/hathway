# 마이그레이션 번호 규칙

> dev-playbook 템플릿. 여러 스레드(또는 사람)가 같은 날 마이그레이션을 더하는 저장소에서 쓴다.
> 도구가 `supabase migration new` 가 아니면 번호를 만드는 명령만 바꾼다. 규칙의 알맹이는 같다.

여러 스레드가 같은 날 마이그레이션을 더하므로 번호(파일 이름 앞의 시각)가 부딪히거나 차례가 뒤섞인다. 한번은
두 스레드가 같은 `090000` 을 골랐고, 늦은 번호가 먼저 main 에 들어간 뒤 이른 번호가 뒤따라 들어오기도 했다.

- **새 파일은 지금 시각의 초 단위 번호로 만든다.** `supabase migration new <이름>` 이 그 번호를 붙인다. `090000` ·
  `130000` 같은 정시 번호를 손으로 고르지 않는다. 정시 번호는 다른 스레드도 고르기 쉬워서 부딪힌다.
- **main 에 머지된 마이그레이션은 고치지 않는다.** 바꿀 것이 있으면 새 파일을 더한다. main 의 DB 와 운영은
  새 파일만 적용하므로, 이미 적용된 파일을 고쳐도 그 DB 에는 닿지 않고 파일과 DB 가 어긋난다.
- **머지 직전에 번호를 main 의 맨 뒤로 보낸다.** `git fetch origin main` 로 받아
  `supabase/migrations/` 를 견준다. 내 파일보다 늦은 번호나 같은 번호가 이미 main 에 있으면 내 파일 이름을 그
  시각의 초 단위 번호로 바꾼다. 그 번호를 인용한 주석과 테스트도 함께 고친다. 이름을 바꾸는 것은 아직 머지되지
  않은 내 파일뿐이므로 위 규칙과 어긋나지 않는다.
- 이름을 바꿨으면 main 를 받아 온 뒤 로컬에서 `supabase db reset` 으로 파일 차례대로 다시 붓고, 마이그레이션이
  닿는 패키지의 계약 테스트를 돌린 다음 민다. 그러면 운영에 적용되는 차례와 파일 차례가 늘 같다.
- ⚠ **두 마이그레이션이 같은 대상을 다시 정의하면 이름 바꾸기가 반드시 필요하다.** 같은 롤 · 같은 표의 GRANT 칸
  목록이나 같은 CHECK 제약이 그렇다. 나중에 적용된 쪽이 앞의 것을 덮으므로 차례가 바뀌면 결과가 달라진다.
  crm 과 legal 처럼 대상이 갈리면 차례가 바뀌어도 결과가 같지만, 그때도 맨 뒤로 보내는 것을 기본으로 한다.
- 기능 브랜치에 프리뷰 DB 가 없는 저장소라면(Supabase Branching 을 끈 경우) 마이그레이션은 로컬 스택에서 붓고 잰다.
