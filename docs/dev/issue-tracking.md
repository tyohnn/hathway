# Linear 이슈를 나누고 읽는 법

루트 `CLAUDE.md` 「개발 과정」 0단계의 자세한 것이다. (dev-playbook 템플릿을 hathway 에 맞췄다.)

요청은 클로드 세션(프로젝트 스레드)에서 들어와 Linear `Pax Humana` 팀(키 `SSO`)의 이슈가 되고 프로젝트 「Hathway 런칭」에 든다. 요청을 받은 세션이 등록한다.

## 요청을 이슈로 나눠 만든다

⚠ **코드를 바꾸지 않는 작업도 이슈로 남긴다.** 빌드 설정, 문서와 규약, Vercel · Supabase 같은 외부 서비스 설정, 사용자가
세션에서 내린 운영 결정이 그렇다. 이슈는 무엇이 언제 왜 바뀌었는지 감사하는 기록이다. PR 이 없으면 본문에 무엇을
어디서 바꿨는지 적는다. 일이 이미 끝난 뒤에 알았으면 그때 만들어 Done 으로 두고 본문에 「사후 등록」이라 적는다. 묻기만
하는 질문은 예외다.

요청 하나를 이슈 하나로 옮기지 않는다. **하위 이슈 하나가 PR 하나**가 되도록 작업의 크기와 의존성을 보고 나눈다.
나누기 전에 저장소를 읽어 요청이 어느 앱과 패키지와 스키마에 닿는지 먼저 확인한다.

**나누는 기준**

- 따로 머지해도 각각 말이 되는 일은 나눈다. web 과 agent 를 함께 바꾸면 대개 나뉜다.
- 마이그레이션과 그것을 쓰는 화면은 나눈다. 스키마는 되돌리기 비싸서 먼저 따로 리뷰받는다.
- 도메인 패키지의 규칙과 포트가 새로 서야 하면, 그것과 앱 배선을 나눈다.
- 리뷰어가 한자리에서 읽기 어려운 크기(하루 넘게 걸릴 일)는 나눈다.
- ⚠ 너무 잘게 나누지 않는다. 커밋 하나로 끝날 일은 이슈 하나다. 루트 `CLAUDE.md` 의 커밋 순서(도구 · 의존성 ·
  골격 · 도메인 · 어댑터 · 앱 · 문서)는 PR **안의** 순서이지 이슈를 나누는 단위가 아니다.

**만드는 법**

- 나눌 것이 없으면 이슈 하나를 만들고 끝낸다.
- 둘 이상으로 나누면 원래 요청을 **부모 이슈**로 만들고 나눈 것을 그 아래 하위 이슈로 단다(`save_issue` 의
  `parentId`). 부모 본문에 요청 원문과 「원본」 줄과 나눈 목록을 두고, 「확인할 것」 질문도 부모에 단다.
- 하위 이슈 제목은 그것만 읽어도 무엇을 머지하는지 알게 쓴다. 본문에는 범위와 끝난 상태(무엇이 되면 머지하는지)를 적는다.
- **앞 이슈가 머지돼야 시작할 수 있으면 `blockedBy` 로 잇는다.** 마이그레이션 → 그것을 읽는 화면, 도메인 포트 → 앱 배선이
  전형이다. 서로 무관한 이슈는 잇지 않아서 따로 시작할 수 있게 둔다.
- 라벨(Bug · Feature · Improvement)은 하위 이슈마다 단다. 상태는 모두 Backlog 다.

## 이슈를 읽는다

- 「시작」을 부모 이슈에 받았으면 하위 이슈를 `blockedBy` 순서대로 하나씩 PR 로 낸다. 막힌 것이 없는 하위 이슈끼리는
  스레드를 따로 세워 함께 진행해도 된다. 막힌 하위 이슈는 앞 이슈가 머지되기 전에 시작하지 않는다.

- `get_issue` 로 본문을, `list_comments` 로 댓글을 모두 읽는다. 본문의 「원본」 줄이 요청한 세션 · 스레드를 가리킨다.
- `needs-answer` 라벨이 붙어 있으면 답이 다 달렸는지 본다. 답이 빠진 질문이 있으면 작업을 시작하지 않고, 무엇이
  빠졌는지 이슈 댓글로 한 번 묻고 스레드에도 한 줄로 알린다.
- 이슈 상태를 **In Progress** 로 옮기고 담당자를 요청한 사람으로 둔다.
